# 企业标书生成平台（BidForge）技术白皮书

> **定位**：企业级 AI 工作流系统设计案例——如何将非结构化业务资料，转化为**可验证、可追溯、可控生成**的业务交付物。
>
> 这不是一个"AI 标书生成系统"的介绍。LangChain、LLM、RAG 只是实现手段；真正的命题是：**如何让 AI 进入企业核心流程，并且让企业敢用**。
>
> 主线七环节：
>
> ```
> 企业业务流程 → 数据治理 → 知识组织 → 智能决策 → 受控生成 → 质量验证 → 企业化治理
> ```
>
> 项目周期：2024.09 – 2025.05 ｜ 七里程碑全部完成（M1–M7），tag v1.1.0

---

## 第一章 背景与业务分析（为什么需要这个系统）

### 1.1 传统标书流程

先讲业务，不讲 AI。一家软件公司接到招标邀请后，标书的诞生是八步纯人工：

```
客户发布招标文件
        ↓
人工阅读 PDF/DOC（几十到几百页）
        ↓
提取需求（技术要求/评分规则/商务要求/格式要求）
        ↓
寻找企业资料（产品/案例/资质/人员/历史项目/售后方案）
        ↓
复制历史标书（同类项目改一改）
        ↓
修改方案
        ↓
人工检查
        ↓
提交
```

### 1.2 四个痛点

**痛点一：信息获取成本高。** 一份招标文件几百页，技术要求、评分规则、商务要求、格式要求混在一起，人工阅读必然遗漏。真正致命的往往是一条埋在第 47 页的★条款。

**痛点二：企业能力难复用。** 注册资本在营业执照、案例在项目部、人员证书在人事处——资料分散保存，每次投标重新寻找，找到的还可能是过期的。

**痛点三：生成不可控。** LLM 确实会写：没有这个资质，它能生成一个；没有这个案例，它能编造金额；没有这个人员，它能虚构经验。投标场景里，这是**商业风险**，不是文本瑕疵。

**痛点四：缺少质量闭环。** 传统流程是"人写 → 人检查"。换成 AI 后变成"AI 写 → 谁检查？"没有检查环节的 AI 生成，等于把企业信誉交给模型概率。

### 1.3 核心判断

> **企业 AI 系统最重要的问题不是生成能力，而是结果可信。**

所以这个系统的所有设计围绕一个铁律展开：

> 生成只允许使用检索证据中出现的数字/资质/年限；证据中没有的量化指标，一律输出【待确认】，绝不编造。

### 1.4 为什么这个场景适合 AI（以及为什么不是 Agent 起点）

投标业务四条全中：输入大量文档（200–500 页）、有明确业务流程（读标→提需求→查能力→写标书→质检→定稿）、有大量历史知识（历史标书/资质/案例/履历）、需要生成大量文本（数万字成稿）。这四条决定了技术路线：**确定性管线，而不是开放式对话 Agent**——每一步的输入输出都可以定义、可以检查、可以回溯。Agent 留给复杂任务探索阶段（见第九章难点 4）。

## 第二章 系统总体架构（一次标书生成经历了什么）

不介绍技术组件，讲数据流。用户上传一份招标文件，数据依次经过七个里程碑引擎：

```
             招标文件
                 |
                 v
          M1 文档解析     —— 把 PDF/DOCX 还原成"章节树 + 内容块"（数据治理）
                 |
                 v
          M2 企业知识库   —— 企业资料结构化：向量管找、能力卡管事实（知识组织）
                 |
                 v
          M3 需求匹配     —— 逐条判断"要求 vs 能力"并绑定证据（智能决策）
                 |
                 v
          M4 标书生成     —— 在证据边界内生成章节（受控生成）
                 |
                 v
          M5 质量检查     —— 生成后再次验证（质量验证）
                 |
                 v
          M6 工作台       —— 人工接手：编辑、确认、终版
                 |
                 v
          M7 企业治理     —— 认证/RBAC/审计/版本/任务中心/监控/评估
```

### 2.1 六大核心实体

数据模型围绕一条链展开：

| 实体 | 含义 | 回答的问题 |
|---|---|---|
| Tender | 招标项目 | 这是哪次投标？ |
| Requirement | 需求 | 甲方要求我们提供什么？ |
| Evidence | 证据 | 这话哪来的？（EVD-xxxx，四元溯源） |
| Capability | 企业能力 | 我们能提供什么？（CAP-xxxx 能力卡） |
| BidDocument | 生成标书 | 我们怎么响应？ |
| QualityReport | 质量报告 | 生成的标书可信吗？ |

### 2.2 设计核心：一条可追溯的数据链

> **我的设计核心不是让模型直接生成标书，而是围绕需求、证据、生成结果建立了一条可追溯的数据链。**

链上的三个"任何"是系统与普通 RAG 项目的分界线：

- 任何一条需求，能回答"从招标文件哪一页哪一节提取的"；
- 任何一句生成内容，能回答"依据哪条证据"（EVD-xxxx → 文件/章节/页码/原文）；
- 任何一次生成，能回答"当时用的企业知识是哪个版本"。

### 2.3 一个贯穿案例：智慧园区项目（T-M3 验收基线）

```
4 份招标文件（PDF/DOCX/Excel/附件）
  → 解析出 421 条原始需求（含 13 个评分点）
  → 知识库 8 份企业资料（14 张能力卡）
  → 需求标准化收敛为 33 条规范需求
  → 匹配分布：FULL 17 / PARTIAL 6 / MISSING 5 / UNKNOWN 5
  → 生成 8 章 26 章节标书（81 处证据引用全部有效）
  → 质检基线得分 99.1，9 组变异注入全部被抓
  → finalize 产出 final.docx / final.md / quality-report.json
```

这组数字是后面各章验收数据的来源。统一口径：**基于项目内置离线评估集与样例数据，不代表通用准确率**。

## 第三章 文档解析：结构恢复（输入理解）

### 3.1 不说"PDF 解析"，说"文档结构恢复"

"PDF 转文本"不是理解。招标文件是有结构的：章节层级、表格、评分细则、★条款，结构承载了需求的重要性和来源。把 PDF 糊成一串文字，等于丢掉一半信息。

四类输入（PDF/DOCX/Excel/扫描件）各走解析器，统一恢复为章节树 + 内容块。原文：

```
第三章 技术要求
   3.2 设备能力
      "设备接入不少于2000台"
```

系统保存的是：

```
document:  招标文件.pdf
section:   第三章 技术要求 → 3.2 设备能力
paragraph: 设备接入不少于2000台
source:    page=47
```

### 3.2 四元溯源：数据治理的第一环

```
文件 → 章节 → 页码 → 原文
```

位置信息不参与生成，但全程跟着数据走：后续的**证据引用**指回它、**质量检查**拿它核对、**响应表**按它定位。

> **设计要点：后续生成不是引用向量结果，而是引用可定位证据。**

### 3.3 需求抽取的三层工程约束

- **窗口切分**：≤4000 字送入模型，页码标记【第p页】只在临时文本存在——模型读得进，出处跟得上。
- **JSON Schema + Pydantic 校验**：输出必须符合需求结构，不合法自动重试 3 次——用程序兜住模型的格式自由。
- **去重编号**：REQ-xxxx 唯一锚点，为匹配/覆盖检查铺路。

### 3.4 关键判断：评分标准表不走 LLM

"商务 40 分：案例 ≥3 个得 5 分……"这类表**用规则引擎解析**。原因：大模型读表不可靠（漏行、串列、读错权重），而评分表格式有限可枚举——规则解析又准又便宜。这是"能确定性的就确定性"原则的第一次应用。

### 3.5 验收数字（M1）

样例四件套端到端：421 条需求 / 13 个评分点（技术 9 + 商务 4，权重和 70）/ 预埋基线 14/14 召回 / ★条款 16 条全部抓取（含"项目经理 5 年"）/ 量化数字原样保留。

## 第四章 企业知识库：不相信向量

### 4.1 核心思想：向量解决"找到"，不能证明"拥有"

普通 RAG 的问题一句话：**向量只解决"找相关内容"，不能证明"企业真的拥有这个能力"。**问"张伟做过多少个项目？"让模型理解一段履历，可能答错、串人、把"参与"算成"负责"。投标场景里，这个错误就是废标。所以知识库做成双层：

```
                企业知识
              /          \
        Chunk             Capability
        找内容             管事实
```

- **Chunk（语义检索层）**：8 类资料 ~600 字切块嵌入，解决"相关资料在哪里"。引擎透明：Milvus 可用走 HNSW/COSINE，挂掉自动降级 SQLite 暴力余弦，engine 字段如实标明——**降级不宕机，且不撒谎**。
- **Capability（结构化能力卡）**：全局编号 CAP-xxxx，把事实锁进结构：

```json
{ "id": "CAP-001", "type": "设备能力",
  "attributes": { "设备接入": "2000台" },
  "source": "产品资料.pdf 第 2 页" }
```

向量找到的是"公司具备设备接入能力"这句话；能力卡保存的是"设备接入：2000 台"这个可比较的值。

> **生成时，数字只能来自 Capability。**

为什么不让模型自己理解？因为**结构化字段可以被规则引擎直接比较**（"招标要 5000 台，卡片是 2000 台 → 不满足"），可以被检查器直接核对（"标书写 2000 台，卡片是 2000 台 → 一致"）。模型理解是概率，结构比较是确定。

### 4.2 两条铁的口径

- **历史标书只切块，不抽能力卡**——历史标书是"我们当年怎么写的"，不是"我们现在是什么样"。它只能当写作风格参考，绝不进事实区。旧项目写的"1250 台"如果被当成现状，就是事实事故。
- **证据验证回原文精确匹配**——每条证据引用都要回到解析产物里精确比对原文，对不上就是 INVALID。

### 4.3 验收数字（M2）

8 类样例资料全部解析入库（14 张能力卡）；6 条语义检索基线全部命中且出处正确（张伟 6 年 / 设备接入 2000 台 / 员工 320 / 质保 3 年 / ISO9001 编号 / 案例 1250 万）；能力卡事实核对通过；Milvus 与 SQLite 降级双引擎路径均实测通过。

## 第五章 需求匹配：辅助判断，不替企业做决定

### 5.1 定位：系统辅助企业判断需求覆盖情况

不说"AI 判断是否满足需求"，说**辅助**。系统产出的是"状态 + 证据"，判断权留给投标经理。

### 5.2 匹配流程

```
招标需求（REQ-C-xxxx）
     ↓ 需求结构化（数据治理）
去重 → 聚类 → LLM 归并 → 10 类分类 → 约束结构化
     ↓ 检索企业能力（知识组织）
规则引擎（数值比较/单位归一） + 能力卡 + 语义检索（双下限 Rerank）
     ↓ 证据绑定（数据治理）
证据验证：引文回原文精确匹配（VALID/INVALID）
     ↓ 冲突仲裁
来源权威 + 时间仲裁（正式资料 > 历史标书；新版本 > 旧版本）
     ↓ LLM Judge（严格 JSON + 证据编号白名单铁律）
     ↓
匹配结果 MAT-xxxx：状态 + 证据链
```

逐条需求得到一条匹配结果：

```
需求：ISO9001 质量管理体系认证
状态：FULL
证据：企业资质.pdf 第 3 页（证书编号 00222Q12345R0S，原文回验通过）
```

### 5.3 四状态：企业系统必须有的严谨性

| 状态 | 含义 | 口径 |
|---|---|---|
| FULL | 有明确证据 | 证据回验通过 |
| PARTIAL | 部分满足 | 如"工期 ≤12 月"只有历史标书证据 → 置信度打折 |
| MISSING | 存在需求但明确没有能力 | 招标要 5000 台，正式资料写 2000 台 → 带相反证据 |
| UNKNOWN | 无法判断 | 没有任何证据 |

**为什么 UNKNOWN 和 MISSING 必须分开？因为"没有找到 ≠ 不具备"。**把"没找到"写成"不满足"，企业自己放弃资格；把"没找到"写成"满足"，等于造假。四状态让标书只能如实陈述——这是企业系统必须有的严谨性，也是普通 AI 项目最容易混为一谈的地方。

### 5.4 冲突仲裁与 LLM Judge 的边界

同一条事实有冲突（正式资料 2000 台 vs 旧宣传册 1250 台）时，仲裁是**确定性的**：来源权威优先、时间新者优先，规则解决不了的标 UNKNOWN。LLM Judge 只做规则做不了的综合判断，且被一条铁律约束：**Judge 引用的每个证据必须来自检索阶段给出的编号白名单**——模型可以判断，但不能凭空"想起"一个证据。

### 5.5 验收数字（M3）

HTTP 端到端 47/47 全 OK：36 条原始需求收敛为 33 条规范需求；分布 FULL 17 / PARTIAL 6 / MISSING 5 / UNKNOWN 5；预埋基线全命中；冲突 time 仲裁生效；FULL 17 条全部至少 1 条 VALID 证据且四元溯源非空；响应表双形态 33 行，证据链可追溯到原文。

## 第六章 标书生成：LLM 组织语言，不生成事实

### 6.1 核心：不是"LLM 生成标书"

而是：

```
需求 + 证据 + 章节规划
        ↓
   LLM 组织语言
```

输入三件套：

- **章节定义**：要写哪一章、什么结构（8 章 26 章节，四段 + 封面/目录/投标函/响应表）；
- **需求列表**：这章要响应哪些需求；
- **证据池**：允许引用哪些证据（带四元溯源）。

两条约束铁律：

- **没有证据 → 禁止生成**（MISSING/UNKNOWN 不声称具备）；
- **数字无法追溯 → 【待确认】**（证据中没有的量化指标原样标注）。

### 6.2 三类信息分治

生成上下文把可用材料分三类，模型对每一类有不同的权限：

| 分类 | 含义 | 例子 | 权限 |
|---|---|---|---|
| FACT | 事实 | 注册资本 5000 万、ISO9001、张伟 6 年经验 | **必须来自证据**，且原样引用 |
| WRITING_STYLE | 表达方式 | 历史标书"项目实施方案通常分为四阶段" | 可以参考行文，不可取事实 |
| INFERENCE | 推理 | 基于事实的合理推演 | **必须标记**，且过检查器 |

### 6.3 四类章节，四种生成策略

不是所有章节都值得用 LLM：

| 章节类型 | 策略 | 例子 |
|---|---|---|
| 固定格式 | 确定性模板 | 封面、目录、投标函 |
| 事实型 | 模板 + 能力卡填充 | 公司简介、资质说明 |
| 方案型 | LLM + 证据注入 | 系统架构、实施方案 |
| 表格型 | 结构化行渲染 | 需求响应表 |

方案型章节 LLM 失败时**回退事实模板**——宁可章节平淡，不产生空章节。

### 6.4 组装与任务状态机

需求响应表三列（招标要求 | 企业响应 | 证据）如实陈述四状态；组装 Markdown + DOCX 双输出（中文宋体防乱码）；任务状态机：断点继续、单章节重生成（version+1）、并发防护（409）、SSE 流式进度。

### 6.5 验收数字（M4）

HTTP 端到端 18/18 全 OK：26 章节全部生成；33 条需求全映射；**整本 81 处 EVD- 引用全部 ∈ 证据池 87 条，无一处编造**；能力卡数值原样落章（注册资本 5000 万 / ISO9001 / 张伟 + PMP + 6 年不串线）。

## 第七章 质量控制：生成后再次验证

### 7.1 一句话

> **系统生成内容后，不直接交付，而是再次验证。**

生成引擎的约束是"事前"，质检是"事后"，两者合起来才是可信系统。质检引擎**只检查、不重写**——自动修复仅限格式类（行尾空白/空行/标题空格），绝不碰企业事实。

### 7.2 三层检查

**第一层：事实检查**

```
标书：设备数量 5000 台
证据：2000 台
→ 发现冲突
```

实现：Layer A 成员资格（事实区数字必须 ∈ 证据/需求/能力卡语料）+ Layer B 锚定比较（32 字符窗口含全部锚点关键词，防"质保 3 年 vs 张伟 3 年"串线）+ 证书双向校验（伪造 token ISO9001→9002、过期 → CRITICAL）。

**第二层：引用检查**

```
EVD-001 是否存在？
是否属于当前项目？
是否属于该需求绑定的证据集？
```

三道都过才算有效引用。注入一个不存在的 EVD-9999 会被立刻抓出。

**第三层：需求覆盖**

```
需求：质保三年
正文：是否响应？
```

需求完整性（响应表行 + 章节正文双重检查，★/高重要缺失 → CRITICAL）、评分项覆盖、章节完整性、项目名一致性、跨章节冲突（同指标数值不相交 → CONFLICT）。

### 7.3 五维评分 + 人工闭环

- 五维：完整性 / 事实准确性 / 证据覆盖 / 一致性 / 格式完整性，每维 = clamp(100 − Σ严重度权重)，CRITICAL=20 / ERROR=10 / WARNING=3 / INFO=0.5。
- 最终产出 **QualityReport**（JSON + Markdown 双形态，按严重度分组 + 待确认汇总）。
- 人工闭环：PATCH 确认/忽略/修复 → review_records 审计留痕 → finalize：CRITICAL/ERROR 未清 → 409 拒绝发布；清完 → final.docx + final.md + quality-report.json 三件套。

```
生成 → 检查 → 人工确认 → 终版
```

### 7.4 验收数字（M5）

**这是整个项目最大的亮点：系统自己生成的东西，系统自己不信，要过一遍检查、过一遍人。**

## 第九章 技术难点：五个"为什么"

### 难点 1：如何避免幻觉？

**回答：证据约束 + 数字校验 + 生成后检查，三道闸。**

生成前证据白名单（没有证据禁止生成、数字无法追溯标【待确认】）→ 生成后确定性校验器（成员资格 + 锚定比较防串线）→ 引用三重检查。实测：81 处引用零编造、9 组注入变异全被抓。

### 难点 2：为什么不用纯 RAG？

**回答：RAG 只能找文本，不能管理企业事实。**

检索回答"像不像"，投标要回答"对不对"。所以知识分两层：Chunk 找内容、Capability 管事实，生成时数字只能来自结构化能力卡，证据必须回原文精确匹配。RAG 在系统里的角色是匹配引擎的一段检索能力，不是项目本身。

### 难点 3：为什么规则优先？

**回答：企业场景错误成本高，能确定性的就确定性。**

评分表解析、数字校验、冲突仲裁、格式修复全部规则化——因为它们的格式有限可枚举，规则又准又便宜；大模型读表漏行串列是真实事故。LLM 只用在必须语义理解的地方（需求归并、方案章节、语义覆盖审查），且每次都被结构约束兜底。

### 难点 4：为什么没有直接上 Agent？

**回答：标书流程高度确定，优先保证可靠性；复杂任务探索阶段再引入 Agent。**

七段管线（解析→提取→检索→生成→检查→交付）每一步的输入输出可定义、可检查、可回溯，编排框架是多余依赖。自研任务中心（TSK-xxxx 登记/进度/取消）+ trace/span 监控已经满足长任务工程化需求。当需要"自动规划投标策略、自动拆解子任务"时，Agent 编排框架 + 已就位的任务底座就是演进路径。

### 难点 5：如何保证可追溯？

**回答：四元溯源贯穿全链。**

文件 → 章节 → 页码 → 原文。需求提取带出处、证据引用回原文、生成快照知识库版本、质检定位原文、审计留痕到人。任何一句标书都能回答"这话哪来的"。

## 第十章 系统演进

### 10.1 存储演进的正确表述

不是"demo 用 SQLite，生产换 PostgreSQL"。

**当前版本为降低部署复杂度，采用 SQLite 完成端到端验证（每操作独立连接 + WAL）；数据访问全部收敛在 Database 封装层，业务逻辑不感知存储实现——生产环境迁移 PostgreSQL 时，改动集中在存储层，六大实体模型与七段管线不动。**

演进路径：

```
SQLite（单机验证，当前）
    ↓
PostgreSQL（多用户并发 + 事务）
    ↓
Redis 缓存（检索/聚合热点）
    ↓
对象存储（原文与产物文件）
    ↓
分布式任务队列（长任务解耦，替代进程内 BackgroundTasks）
```

### 10.2 能力演进

- **数据规模**：SQLite → PostgreSQL + 对象存储（上一节）。
- **模型能力**：确定性管线 → 多 Agent 协作——当需要自动规划投标策略时引入 Agent 编排，任务中心与 trace 监控已铺好工程底座。
- **企业协同**：单用户 → 多人审批流程——M7 的 RBAC/审计/成员/版本已就位，下一步是完整审核工作流（编辑 → 审核 → 复核 → 发布）与多人协同编辑。

### 10.3 一句话总结

这个项目不是普通"AI 项目"，而是 **AI + 企业软件工程 + 知识工程 + 质量治理**的综合系统：七里程碑建成一条从招标文件到可交付标书、全程可追溯、事实受约束的生产线——全量离线回归 290 passed，各里程碑 HTTP 端到端验收 47/47、18/18、23/23、30/30、52/52 全 OK。
