# 面试问答手册（白皮书第十一章）

> 目标不是背白皮书，而是形成三层介绍：**30 秒说清定位 → 3 分钟讲透主线 → 10 分钟随问随深挖**。
> 口径：文中数字均为项目内离线验收实测，如实回答，不夸大。

---

## 一、30 秒介绍（电梯陈述）

> 我负责开发一个企业级标书生成平台，核心解决企业投标过程中**资料分散、需求分析困难以及 AI 生成不可控**的问题。系统通过文档解析、企业知识库、需求匹配、受控生成和质量检查形成闭环，其中重点设计了**证据约束和事实一致性校验机制**，保证生成内容可追溯。

记忆锚点：三个词——**可验证、可追溯、可控生成**。

## 二、3 分钟介绍（主线陈述）

**第一分钟：业务与定位**

传统标书流程八步纯人工，四个痛点：信息获取成本高（几百页 PDF 人工易遗漏）、企业能力难复用（资料分散每次重找）、生成不可控（LLM 编造资质/金额/经验 = 商业风险）、缺少质量闭环（AI 写 → 谁检查？）。所以核心判断：**企业 AI 系统最重要的问题不是生成能力，而是结果可信。**

**第二分钟：系统主线**

系统是七段确定性管线（不是对话 Agent）：文档解析 → 企业知识库 → 需求匹配 → 标书生成 → 质量检查 → 工作台 → 企业治理。围绕六个实体（招标项目/需求/证据/能力/生成标书/质量报告）建立一条可追溯数据链：任何一句标书都能回答"这话哪来的"。

三个关键设计：① 知识双层——向量管找、能力卡管事实，生成时数字只能来自结构化能力卡；② 四状态匹配——FULL/PARTIAL/MISSING/UNKNOWN，**没有找到 ≠ 不具备**；③ 质检三层——事实检查/引用检查/需求覆盖，系统生成的东西系统自己不信，要过一遍检查、过一遍人。

**第三分钟：结果与工程**

七里程碑完成，全量离线回归 290 passed，各里程碑 HTTP 端到端验收 47/47、18/18、23/23、30/30、52/52 全 OK。可复述的关键实测：81 处证据引用零编造；9 组变异注入（篡改数字/伪造证书/假引用）全部被抓；企业级能力（RBAC/审计/知识版本/任务中心/链路监控/评估体系）齐全。

## 四、精选问答

### Q1 用一句话介绍这个项目？

一句话：一个把"招标文件 + 企业资料"变成"可交付标书"的企业级 AI 工作流系统，核心命题是**结果可信**——AI 生成的一切必须能回溯到证据。
→ 白皮书 引言 + 第二章

### Q2 为什么说"RAG 不是项目"？

一句话：RAG 只解决"找"，投标要解决"对不对"，所以核心是需求 × 能力的双向结构化，检索只是其中一段。

展开：向量检索找到的是"像"的段落，不能证明"企业真的拥有这个能力"。系统把企业知识做成两层——Chunk 找内容、能力卡管事实；匹配是两张结构化表的关系运算，生成带证据注入，检查拿结构化字段做确定性比较。
→ 白皮书 4.1、5.2

### Q3 你的知识库怎么设计的？

一句话：**向量负责找，结构化负责证明**——双层设计。

展开：Chunk 层 8 类资料切块嵌入，Milvus 挂自动降级 SQLite 暴力余弦（engine 字段透明标识，降级不撒谎）；Capability 层把事实锁进能力卡（`CAP-001 设备接入 2000 台`），规则引擎直接比较数字，不让模型去"理解"。历史标书只切块不抽卡——它是写作风格参考，绝不是企业事实。生成时数字只能来自 Capability。
→ 白皮书 第四章

### Q4 大模型幻觉怎么控制？

一句话：三道闸——生成前证据白名单、生成后确定性校验器、引用三重检查；只检查不重写。

展开：生成前没有证据禁止生成、数字无法追溯标【待确认】；生成后 Layer A 数字必须 ∈ 证据/需求/能力卡语料 + Layer B 锚定比较（32 字符窗口）防"质保 3 年 vs 张伟 3 年"串线；引用必须 ∈ 证据池、∈ 当前项目、∈ 该需求绑定证据。实测：81 处引用零编造；9 组变异注入全部被抓。
→ 白皮书 6.1、7.2、第九章难点 1

### Q5 MISSING 和 UNKNOWN 有什么区别？

一句话：MISSING 是"资料明确显示不满足"，UNKNOWN 是"没有证据"——**没有找到 ≠ 不具备**。

展开：把"没找到"写成"不满足"，企业自己放弃资格；写成"满足"，等于造假。四状态让标书只能如实陈述：MISSING 带相反证据（招标要 5000 台，正式资料写 2000 台），UNKNOWN 标"待确认"。历史标书证据不能覆盖正式项目资料。这是企业系统必须有的严谨性。
→ 白皮书 5.3

### Q6 怎么保证需求被完整响应？

一句话：确定性规则做完整性检查，不做概率性判断。

展开：需求完整性（响应表行 + 章节正文双重检查，★/高重要缺失 → CRITICAL）、评分项覆盖（关键词未出现 → SCORE_MISSING）、章节完整性 + 项目名一致性 + 跨章节冲突。LLM 只补语义覆盖二次审查（covered/not + 理由），数字/证书/证据存在性全由确定性程序负责。
→ 白皮书 7.2

### Q7 质量怎么量化？

一句话：五维评分 + 变异注入验收——系统自己生成的东西，系统自己不信。

展开：五维（完整性/事实准确性/证据覆盖/一致性/格式完整性）= clamp(100 − Σ严重度权重)，CRITICAL=20/ERROR=10/WARNING=3/INFO=0.5。验收不是"看着还行"，而是注入 9 组变异（2000→5000、ISO9001→9002、注入 EVD-9999……）要求全部被抓。finalize 有 CRITICAL/ERROR 未清就 409 拒绝发布。
→ 白皮书 7.3、7.4

### Q8 评分标准表为什么不用 LLM 解析？

一句话：大模型读表不可靠，评分表格式有限可枚举，规则解析又准又便宜。

展开：漏行、串列、读错权重是 LLM 读表的常见事故，评分表直接影响商务决策。贯穿全项目的原则是**能确定性的就确定性**：评分表规则解析、冲突仲裁按来源权威/时间、固定格式章节用模板——LLM 只用在必须语义理解的地方。
→ 白皮书 3.4、第九章难点 3

### Q9 项目里最难的问题是什么？

一句话：事实正确性——"不能写错"比"写得快"重要，所有难点都从它长出来。

展开：三个子问题各配解法并验收证明：数字串线（质保 3 年 vs 张伟 3 年）→ 锚点比较；证据编造 → 白名单 + 三重引用检查；知识冲突（正式资料 2000 台 vs 旧宣传册 1250 台）→ 确定性仲裁（来源权威 + 时间）。
→ 白皮书 5.4、7.2、第九章

### Q10 为什么没有直接上 Agent？

一句话：标书流程高度确定，优先保证可靠性；复杂任务探索阶段再引入 Agent。

展开：七段管线每一步的输入输出可定义、可检查、可回溯，编排框架是多余依赖；自研任务中心（登记/进度/取消）+ trace/span 监控已满足长任务工程化。当需要"自动规划投标策略、自动拆解子任务"时，Agent 编排 + 已就位的任务底座就是演进路径。
→ 白皮书 第九章难点 4

### Q11 企业级能力（权限/审计/版本）为什么需要？

一句话：能跑通 ≠ 能上线——权限管谁能看、审计管谁干了、版本管"当时用的什么知识"。

展开：RBAC 5 角色 × 17 权限 + 项目成员三段判定（持 final:view 也必须是项目成员才能看终版）；13 类关键动作审计留痕仅 admin 可见；知识库每次变更自动升版（KV-xxxx + {日期}-v{n}），生成任务快照版本号——终版被质疑时能回答"当时用的企业资料是哪个版本"。
→ 白皮书 第八章

### Q12 任务中心 / Trace 解决什么问题？

一句话：AI 链路不是黑盒——任务统一登记、trace/span 两级留痕、监控旁路绝不打断业务。

展开：5 类任务（提取/知识处理/匹配/生成/质检）统一 TSK-xxxx 登记：进度可见、cancel 仅 pending（本人可取消/他人 403/running 409）、非 admin 只见自己任务；trace/span 记录调用了什么、哪一步失败、谁启动的；LLM 调用指标单独统计。
→ 白皮书 第八章

### Q13 这个项目你从 0 到 1 怎么推进的？

一句话：里程碑式推进，每个里程碑"代码 + 测试 + HTTP 端到端验收报告"，验收脚本入库可复跑。

展开：M1–M7 每个里程碑交付三件套：实现 + 离线测试 + 端到端验收脚本（scripts/verify_m*.py，输出报告，退出码恒 0 便于 CI）。验收暴露的真实缺陷全部记录在案并带回归测试（Milvus 连接 60s 冷却、outline 映射未落库、WindowsPath startswith TypeError、pytest 默认跳过未配置）。数字口径一律声明"基于项目内离线评估集，不代表通用准确率"。
→ 白皮书 10.3、ROADMAP 各里程碑验收段

### Q14 评估数字怎么理解？（防追问）

一句话：Recall@10=0.9231 / MRR=0.7173 是 13 条基线在内部离线评估集上的检索质量，是迭代标尺，不代表生产准确率。

展开：评估对象是 T-M3 基线（36 条需求 + 8 份资料）；生成评估 4 指标离线全 1.0 意味着"确定性约束生效"，不是"模型完美"。所有响应带 disclaimer，这是诚实口径的一部分。真实效果验证要靠真实招标文件 + 真实 LLM 的集成测试与人工复核。
→ 白皮书 8 验收数字、10.4

### Q15 如果重来一次，你会改什么？

一句话：三个"更早"——更早做评估框架、更早做审计、更早做知识版本化。

展开：评估框架（离线评估集）如果 M1 就有，每个里程碑都有量化尺子；审计更早建立，早期"验收中发现并修复"的缺陷会更快定位；知识版本化更早做，M2 的重传覆盖旧卡语义（已知限制）会更稳。没改的部分：事实约束铁律、四状态口径、只检查不重写——这三条从第一天定下，被证明是对的。
→ 白皮书 10.2、README 已知限制

### Q16 存储为什么用 SQLite？生产怎么办？

一句话：为降低部署复杂度完成端到端验证，数据访问收敛在封装层，迁移 PostgreSQL 改动集中在存储层。

展开：当前 SQLite（每操作独立连接 + WAL）完成七里程碑验证；业务逻辑不感知存储实现，六大实体与七段管线不随存储迁移变动。演进路径：PostgreSQL（并发/事务）→ Redis（热点缓存）→ 对象存储（文件）→ 分布式任务队列（长任务解耦）。
→ 白皮书 10.1

## 五、高频追问补充（面试官实测高频，Q17–Q21）

> 这 5 问是面试中出现率最高的追问，标准答案已定稿。Q17/Q21 分别与 Q2/Q10 呼应——前者是初问，这里是追问深挖版。

### Q17 为什么不用直接 RAG 生成标书？

一句话：**标书场景不是简单问答，而是企业交付场景。RAG 解决信息召回，但无法保证企业事实正确**，所以增加 Capability 结构化事实层 + 生成后质量验证。

展开：RAG 能回答"资料里写了什么"，不能回答"标书里这个数字对不对"。企业交付物的事实错误是商业风险，不是体验问题。所以系统把 RAG 降为一段检索能力，在它之上加两层：生成前的能力卡事实约束（数字只能来自结构化能力卡）、生成后的确定性质量检查（每个数字回对证据）。
→ 白皮书 4.1、第九章难点 2；源码 `services/capability_extractor.py`、`quality/checks/facts.py`

### Q18 为什么要设计 Capability？（核心亮点）

一句话：**向量检索适合解决"在哪里"，企业业务需要回答"是否真实拥有"**——不应依赖模型从文本中推理，因此单独建立能力卡。

展开：向量检索本质是相似度排序，它找到的是"像"的段落，不是"对"的事实；"企业到底有没有 2000 台设备接入能力"这个问题的答案必须可比较、可验证、可审计。所以把企业事实结构化进能力卡（CAP-xxxx + attributes），匹配用规则引擎直接比较数字，生成只引用能力卡数值，质检拿能力卡做确定性基准。
→ 白皮书 4.2；源码 `capability_extractor.py:156 CapabilityExtractor`、`matching/rules/rule_engine.py:149 RuleEngine`

### Q19 为什么 MISSING 和 UNKNOWN 要区分？

一句话：**企业场景中没有找到证据，不代表企业没有能力。混淆会导致系统错误拒绝企业参与投标。**

展开：把"没找到"写成"不满足"，企业自己放弃资格；写成"满足"，等于造假。四状态让标书只能如实陈述：MISSING 带相反证据（招标要 5000 台，正式资料写 2000 台），UNKNOWN 标【待确认】等待人工补齐资料。这是企业系统必须有的严谨性——宁可多一步人工确认，不能替企业做假判断。
→ 白皮书 5.3；源码 `matching/models/match_result.py:23 MatchStatus`

### Q20 为什么生成后还需要检查？

一句话：**LLM 擅长语言组织，不适合作为事实数据库。生成和验证分离——生成负责表达，检查负责可信。**

展开：让同一个模型既写内容又验内容是自欺欺人。系统的态度是"自己生成的东西自己不信"：质检引擎全部确定性程序（数字成员资格、锚定比较、引用三重检查、需求覆盖），LLM 只补语义覆盖审查一层；发现问题不自动重写，人工确认后走 finalize 闭环（未清 CRITICAL 直接 409 拒绝发布）。
→ 白皮书 7.1、7.4；源码 `quality/runner.py:54 QualityRunner`、`quality/checks/facts.py:56 check_facts`

### Q21 为什么没有用 Agent？（非常加分）

一句话：**这个阶段标书流程具有高度确定性，优先保证流程可控和结果可信。Agent 更适合开放探索任务**，后续在研究型任务中可以引入 Agent 编排。

展开：七段管线每一步的输入输出都可定义、可检查、可回溯，编排框架是多余依赖，而且多 Agent 的动态路径会破坏"结果可信"这条主线。已就位的自研任务中心（登记/进度/取消）+ trace/span 监控满足长任务工程化需求。当需要"自动规划投标策略、自动拆解子任务"这类开放探索时，Agent 编排 + 现有任务底座就是演进路径——不是不用，是分阶段用。（与 Q10 呼应：Q10 是初问版，本条是面试官继续追问"那你们为什么自己写任务系统"时的深挖版。）
→ 白皮书 9.4；源码 `services/task_tracker.py`、`services/trace.py:25 AgentTracer`

## 六、防失分提醒

1. **不要先说技术**——先讲业务痛点与"结果可信"判断，技术是为判断服务的。
2. **不要把 RAG 说成核心**——核心是双向结构化 + 可追溯数据链，RAG 是一段检索能力。
3. **不要夸大数字**——所有验收数字带"内部离线评估集"口径，被追问时主动声明。
4. **不要回避"没用 LangGraph/Agent"**——诚实说明管线确定性优先，任务中心 + 监控已满足工程需求，Agent 是探索阶段方向。
5. **收尾落在价值**——让 AI 进入企业核心流程，并且让企业敢用。这是与普通 AI 项目的分水岭。
